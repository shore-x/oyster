# 通用文件夹浏览器 MVP

> 状态：已实现
>
> 日期：2026-08-10

## 问题与目标

Oyster 需要在应用内浏览由文件夹承载的内容。Artifact 和 Oyster 自身的设计文档都需要这种交互，但它们不因此成为同一种领域对象。

当前方案只定义一个通用文件夹浏览器：调用方提供绝对文件夹路径和界面标题，浏览器展示该路径下的文件树与文件内容。Artifact 列表提供各 Artifact 的目录路径；应用提供随版本发布的设计文档目录路径。来源差异停留在入口，不进入浏览器的核心模型。

## 当前能力

- 递归列出目录中的全部条目，包括 dotfile、无扩展名文件、目录、普通文件、符号链接和其他文件系统条目；
- 符号链接作为叶节点展示，不递归跟随；
- 普通文件按原始字节读取，展示逻辑与文件发现分离；
- `.md` 使用现有安全 Markdown Renderer，其他有效 UTF-8 文件按纯文本展示，无法按严格 UTF-8 解码的文件仍保留在树中并显示暂不支持预览；
- Markdown 普通相对链接和 `[[target]]` / `[[target|label]]` 可以预览并跳转到文件，跳转进入当前浏览历史；
- Artifact 页面提供“浏览”入口，侧栏提供 Oyster 设计文档入口，两者复用同一个页面。

## 最小契约

Renderer 通过 typed preload API 请求完整文件树和单个文件的原始字节。路径由调用方直接提供；当前不增加路径引用、来源 Provider、allowlist、Workspace、Sandbox 或额外权限治理模型。

浏览器是 UI 交互能力，不是 Artifact、Knowledge 或新的持久化领域层。它不拥有文件、不维护索引或数据库镜像，也不负责编辑。后续增加图片、代码高亮等 Renderer 时，应继续保持文件发现、读取和展示分离；在出现多个真实实现之前不提前建设 Renderer 插件注册表。

## 设计文档 Dogfood

构建会把 `docs/` 复制到应用输出中的独立只读资源目录。开发模式直接浏览源码 `docs/`，发布模式浏览随应用构建的对应目录，因此不会把 Oyster 设计文档放进用户的 Knowledge 或 Artifact，也不会改变用户仓库的维护方式。
